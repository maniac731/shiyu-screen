## 1. 我买到的设备是什么

- 主控与屏幕一体板：ESP32-S3-Touch-LCD-7B，分辨率 1024 × 600。
- ESP32-S3 同时支持 2.4GHz Wi-Fi 和 Bluetooth LE，但不支持经典蓝牙。
- 屏幕通过并行 RGB 接口持续刷新，不等同于带完整内部显存的手机屏幕。
- MicroSD/TF 卡不是当前 MVP 的必需品；图片可以通过 Wi-Fi 写入板载 Flash 的 FFat 分区。

## 2. 为什么 Arduino Core 版本会影响屏幕

Arduino IDE 是编辑和上传工具，ESP32 Core 才包含编译器、ESP-IDF 和底层驱动。

- Core 3.3.12 使用 ESP-IDF 5.5.5。
- Core 3.2.1 使用 ESP-IDF 5.4.2，更接近厂商固件使用的 ESP-IDF 5.4-dev。
- 版本变化可能改变 RGB LCD、DMA、PSRAM、Wi-Fi 和缓存调度行为。
- “最新版”不必然是某块具体硬件的最稳定版；硬件项目应固定并记录已验证工具链。

当前选择 Core 3.2.1 作为开发基线，但现有对照不足以证明它的轻微抖动一定少于 3.3.12。选择它主要是因为接近厂商环境且项目可以正常编译。

## 3. 为什么屏幕会轻微抖动

ESP32 需要持续从 PSRAM 读取 1024 × 600 的 RGB565 帧，通过 DMA 按严格像素时钟送给屏幕。PSRAM、DMA 或同步时序出现很小的偏差，就可能在高对比边缘表现为轻微位移。

实际对照结果：

- 厂商 `06_LCD.bin`：正常距离基本看不出，贴近能看到轻微底噪。
- 我们的最小静态版本：正常距离基本看不出，贴近能看到轻微底噪。
- 18MHz / 40 行 bounce buffer：反而更严重。
- 30MHz / 10 行在我们的构建环境中没有变得更稳定。
- 当前保留 18MHz、20 行 bounce buffer、双 framebuffer。

验收边界：正常观看距离不可察觉；允许贴近观察时有与厂商固件相当的轻微底噪；不接受错行、撕裂、上下跳动或持续加剧。

## 4. Mac 供电、充电和天线会导致抖动吗

- Mac 会调节 USB 输出，并不是直接把电池电压送给屏幕。
- 供电严重异常更常表现为重启、黑屏、USB 断连、花屏或 brownout，而不是只有轻微位移。
- Mac 充电与不充电没有复现出稳定差异，因此目前不认为它是主因。
- Wi-Fi 天线弯曲主要影响无线信号；Wi-Fi 完全关闭时，天线不会参与 RGB 刷新。
- 原装海绵的轻微挤压没有证据指向故障，但仍应避免排线、同轴接头和主板接口被铜柱或外壳顶住。

## 5. 图片大小会影响静态抖动吗

JPEG 文件大小只影响上传和解码时间。解码完成后，每张全屏图片都会成为同样大小的 1024 × 600 RGB565 帧，约 1.17MB。

不同图片会影响抖动的“可见程度”：文字、细线和高对比直边容易暴露轻微位移；柔和渐变和复杂照片纹理不容易察觉。

## 6. 为什么使用 Wi-Fi 传图片

当前方案由 ESP32 临时建立本地热点：

1. 屏幕开启 `ShiYu-Screen-A02`。
2. 手机连接热点并打开 `192.168.4.1`。
3. ESP32 内置 WebServer 返回管理网页。
4. 浏览器通过 HTTP POST 分块上传 JPEG。
5. ESP32 边接收边写入临时文件，校验后保存到 FFat。
6. 用户点击完成，固件关闭 Wi-Fi，再恢复图片显示。

整个过程不经过互联网和云服务器。Wi-Fi 适合图片这种较大文件，也允许第一版直接使用手机浏览器，不必先开发 iOS 和 Android App。

## 7. 为什么第一版不使用蓝牙传图片

ESP32-S3 支持 Bluetooth LE，不支持经典蓝牙。BLE 很适合设备发现、亮度、开关、少量库存状态和“请开启 Wi-Fi”之类的小命令。

使用 BLE 传图片需要自行实现切片、编号、确认、丢包重传、断点恢复、拼接和校验，并且需要专门的手机 App 处理扫描、权限、配对与断线。因此成熟版本可以用 BLE 唤醒 Wi-Fi，但第一版仍由屏幕明确开启 Wi-Fi，再用 Wi-Fi 传图片。

## 8. 为什么 Wi-Fi 不能由完全离线的屏幕被手机直接开启

如果屏幕的 Wi-Fi 和蓝牙都关闭，手机与屏幕之间没有通信通道，手机无法远程命令固件开启 Wi-Fi。

第一版流程：

`点击设置 → 连接手机管理 → 固件开启限时 Wi-Fi → 手机管理 → 完成后关闭 Wi-Fi`

未来可以让 BLE 低功耗待机，由手机 App 通过 BLE 唤醒 Wi-Fi。

## 9. 食愈屏幕的产品与交互定位

- 屏幕负责提醒和呈现；手机负责录入和复杂管理。
- 默认可以是安静的相框/环境界面，同时保留库存数量与临期状态。
- 饭点出现餐食建议；真正临期时提高提醒等级；无需全天重复同一推荐。
- 主页面规划为“今日、库存、相框”。
- 右上角长期保留设置齿轮；图片上传、方向、亮度和设备信息都进入设置。
- 页面尽量静态渲染，只在数据或页面变化时更新；避免连续动画、细边框和高频重绘。

## 10. 当前阶段与下一步

当前阶段：Core 3.2.1、18MHz、20 行 bounce buffer、双 framebuffer。正在恢复触摸并验证右上角设置入口，Wi-Fi 暂不启动。

分阶段验收：

1. 静态图片 + 齿轮 + 设置页，确认触摸不会放大抖动。
2. 设置页中的“连接手机管理”开启限时热点。
3. 验证上传、选择、删除、完成退出和自动超时。
4. 验证 Wi-Fi 关闭后恢复到稳定显示。
5. 再开发“今日、库存、相框”三个食愈面板。

## 11. 为什么早期切页会黑一下

黑屏不是屏幕必须经历的过程，而是固件为了掩盖早期切图撕裂而主动关闭约 130ms 背光。当前驱动已经使用双 framebuffer，普通本地页面可以先在内存中完整绘制，再交给驱动在完整帧边界切换。因此照片与设置页之间取消黑屏过渡；只有 Wi-Fi 上传、JPEG 解码或其他高负载操作仍保留熄屏保护。

进一步对照原厂 LVGL 后发现，仅仅配置 `num_fbs = 2` 还不够。旧实现额外申请了第三块全屏缓冲，再整屏复制到驱动缓冲，可能在扫描过程中出现旧页面残行。新实现直接取得驱动的两块 framebuffer：在后台缓冲完整绘制，提交后等待 VSYNC/一帧完成通知，再交换显示缓冲。照片页仍保留在另一块 framebuffer 时，从设置返回可直接切回，不需要重新读取和解码 JPEG。

第一次重构后，进入设置仍比返回照片慢，因为设置页是在点击后才现场绘制，而返回只是切换已缓存照片。随后增加后台预渲染：照片显示完成后立即在未显示 framebuffer 中准备设置页；齿轮和返回操作都只负责在 VSYNC 边界切换已完成页面。

## 12. 页面、framebuffer 与预渲染

### 12.1 页面并不等于一块 framebuffer

页面数量不受两块 framebuffer 限制。一个尚未显示的页面通常只以以下形式存在：

- Flash 中的页面绘制代码；
- Flash / FFat 中的字体、图标和图片素材；
- RAM 中的库存、亮度、网络状态和导航状态；
- 描述按钮坐标、文字排版和颜色的参数。

只有页面准备显示时，程序才按照这些“配方”把完整像素画面绘制进 framebuffer。因此即使将来有 20 个页面，也不需要准备 20 块全屏内存。

### 12.2 什么是单 framebuffer

Framebuffer 是 RAM 中的一段内存，按顺序保存屏幕上每一个像素的颜色。当前屏幕使用 RGB565，每个像素占 2 字节：

```text
1024 × 600 × 2 = 1,228,800 字节 ≈ 1.17 MiB
```

单 framebuffer 意味着屏幕显示外设正在读取这块内存时，程序也在同一块内存上修改下一页。如果屏幕扫描到一半，程序已经改写了后半部分，就可能在同一帧中同时看到旧页面和新页面，产生撕裂、残行或局部闪动。

### 12.3 什么是双 framebuffer

双 framebuffer 使用两块同样大小的完整画面内存：

```text
前台 framebuffer：RGB 外设正在读取和显示
后台 framebuffer：程序在用户看不见的地方绘制下一页
```

后台画完后，程序等待 VSYNC 或一帧完成的边界，再让两块内存交换角色。这样屏幕不会读到一张“画到一半”的页面。

两块 framebuffer 不是固定的“照片区”和“设置区”。它们的身份会不断轮换：

```text
时刻 1：A 显示照片，B 绘制设置页
时刻 2：B 显示设置页，A 等待绘制下一页
时刻 3：A 显示亮度页，B 等待再次使用
```

当前两块全屏 framebuffer 合计约占用：

```text
1.17 MiB × 2 ≈ 2.34 MiB PSRAM
```

### 12.4 早期所说的“三块”是什么

早期实现中存在：

1. RGB LCD 驱动申请的 framebuffer A；
2. RGB LCD 驱动申请的 framebuffer B；
3. 应用额外从 PSRAM 申请的一块全屏临时画布 C。

页面先画到 C，再把约 1.17 MiB 像素复制进驱动 framebuffer。这并不是真正协调良好的三重缓冲，因为 C 没有直接成为屏幕下一帧的扫描源，仍需一次整屏复制。复制如果与屏幕扫描交叠，就可能出现残行和撕裂，而且三块全屏区域合计约占 3.52 MiB PSRAM。

现在的方案取消了 C，直接在驱动提供的后台 framebuffer 上绘制，然后在帧边界交换。

### 12.5 后台预渲染存在哪里

“后台”不是另一个文件，也不一定是另一个线程。它指当前没有被屏幕扫描的那块 framebuffer。当前照片显示完成后，设置页会被预先画进另一块位于 PSRAM 的 framebuffer：

```text
PSRAM
├── framebuffer A：当前照片
└── framebuffer B：预渲染完成的设置页
```

点击齿轮时不再现场绘制，只需在帧边界把 B 变成前台，所以切换很快、没有黑屏，也不会留下旧页面的几行像素。

### 12.6 页面很多、跳转分支很多时怎么办

双 framebuffer 只能同时保留两张完整画面，但页面数量可以很多。常用策略分三层：

1. **唯一或高概率下一页**：提前完整绘制。例如相框页的主要入口只有设置齿轮，就预绘制设置页。
2. **多个候选页面**：提前加载共同字体、图标、数据并计算布局，但不生成全部完整画面。
3. **用户确定目标后**：把目标页面实时绘制到后台 framebuffer，完成后再交换。

例如在设置页点击“亮度”：

```text
设置页正在前台显示
→ 用户点击亮度
→ 在后台 framebuffer 绘制亮度页
→ 绘制完成
→ 在帧边界交换
→ 亮度页完整出现
```

如果之前保存照片的 framebuffer 已被子页面覆盖，返回相框时就从 Flash / FFat 重新读取 JPEG，解码到后台 framebuffer，再交换。没有必要为了每个页面都增加一块全屏缓存。

## 13. 这块硬件由什么组成

这块开发板不是单纯的屏幕，而是一台结构精简的小电脑，可以分成计算、存储、显示、输入、通信和供电六个部分。

### 13.1 ESP32-S3 主控：负责执行和控制

板上标有 `ESP32-S3-WROOM-1U` 的金属模块是核心。ESP32-S3 负责：

- 运行固件和页面逻辑；
- 读取触摸坐标并判断按钮；
- 解码 JPEG 和绘制页面；
- 控制 framebuffer 交换；
- 启动 Wi-Fi、接收手机上传；
- 管理 USB、UART、I²C、GPIO 等接口。

它属于微控制器 MCU：除了 CPU，还集成了无线通信、存储接口和多种外设控制能力。

### 13.2 Flash：断电后仍保留的长期存储

这块设备约有 16 MB Flash，可以类比成小型硬盘。它通常保存：

- 烧录进去的固件；
- 程序代码、字体和图标；
- FFat 文件系统和用户 JPEG 照片；
- 需要断电保存的亮度、方向和网络配置。

Flash 断电后仍能保留内容，但读写通常比 RAM 慢，而且存在擦写寿命，不适合每秒反复写入。所谓“烧录固件”，就是把编译后的程序写入 Flash。

JPEG 保存在 Flash 时还是压缩文件，不能直接作为 RGB LCD 的完整像素画面；显示前需要读取并解码到 framebuffer。

### 13.3 RAM：开机期间的工作台

RAM 用于程序运行和临时计算，读写快，但断电后内容消失。这块设备需要区分两类 RAM。

**内部 SRAM** 位于 ESP32-S3 芯片内部，容量较小但速度快，适合存放：

- 函数局部变量和任务栈；
- 当前页面、触摸坐标和系统状态；
- 信号量、网络控制结构；
- DMA 可以快速访问的小型缓冲区。

**外部 PSRAM** 容量约 8 MB，位于主控外部，容量更大但访问通常比内部 SRAM 慢，适合存放：

- 两块全屏 framebuffer；
- JPEG 解码临时数据；
- 较大的图像和网络缓存。

可以这样记：

```text
Flash：仓库，断电后东西还在
内部 SRAM：手边的小工作台，快但空间有限
PSRAM：旁边的大工作台，容量大但稍慢
```

### 13.4 RGB LCD：把像素变成画面

LCD 面板只负责接收并显示像素，不理解“库存”“设置”或“按钮”。RGB 接口持续向它发送：

- 红、绿、蓝颜色数据；
- 像素时钟；
- 行同步、场同步和数据有效信号。

即使画面完全静止，显示外设仍然反复读取 framebuffer 并刷新屏幕。这就是像素时钟、DMA、PSRAM 带宽和同步时序会影响稳定性的原因。

### 13.5 DMA 与 bounce buffer：负责搬运像素

DMA 可以在不让 CPU 逐个像素搬运的情况下，把图像数据持续送给 RGB LCD。当前链路可以简化为：

```text
PSRAM framebuffer
        ↓
内部 SRAM 的 bounce buffer
        ↓ DMA
     RGB LCD
```

当前 bounce buffer 高度约为 20 行，单块大小约为：

```text
1024 × 20 × 2 ≈ 40 KiB
```

驱动通常使用两块轮流中转，合计约 80 KiB：一块正在送屏，另一块准备后续像素。它连接了容量大的 PSRAM 与适合稳定高速传输的内部内存。

### 13.6 触摸控制器：只报告触点

LCD 负责输出，触摸控制器负责输入，两者是不同系统。触摸控制器通过 I²C 等接口报告触点数量与坐标，例如：

```text
1 个触点，x=935，y=62
```

ESP32 再根据当前页面和按钮区域判断这是齿轮、Back 还是其他操作。触摸控制器本身并不知道按钮含义。控制器能报告五点触控，不代表产品必须采用五指手势；具体交互仍由固件决定。

### 13.7 Wi-Fi、Bluetooth LE 与外接天线

ESP32-S3 支持 2.4GHz Wi-Fi 和 Bluetooth LE。当前外接小天线同时服务这两种无线通信。

- Wi-Fi 适合传输图片、网页和较大数据；
- BLE 适合设备发现、少量配置、控制命令和唤醒 Wi-Fi；
- 天线影响无线信号，不直接参与 framebuffer 到 LCD 的像素传输。

### 13.8 USB、UART、BOOT 与 RESET

- **USB**：供电、烧录固件、串口日志及 USB 设备功能。
- **UART**：电脑与 ESP32 之间的串行通信，可用于日志、诊断和烧录辅助。
- **BOOT**：上电时按住可让芯片进入下载/烧录模式。
- **RESET**：重新启动正在运行的固件，不会自动清空 Flash 中的程序和照片。

因此黑屏不必然表示硬件损坏，也可能只是固件没有正常启动或没有正确驱动显示。重新上电会清空 RAM，但不会清空 Flash。

### 13.9 电源与背光

板上的稳压与电源管理电路会把 USB 输入转换成主控、Flash、PSRAM、LCD 和触摸控制器需要的电压。LCD 背光还有独立的驱动与亮度控制。

降低背光亮度时，framebuffer 内的像素值可以完全不变，只是背光功率下降，所以人眼看到整块屏幕变暗。`BAT 4.20V` 是电源状态信息，不是内存容量。

## 14. 一张照片从手机到屏幕经历了什么

```text
1. 手机通过 Wi-Fi 上传 JPEG
2. ESP32 的 Wi-Fi 模块接收数据
3. JPEG 文件写入 Flash 的 FFat 文件系统
4. 需要显示时，程序从 Flash 读取 JPEG
5. ESP32 将 JPEG 解码为 RGB565 像素
6. 像素直接写入 PSRAM 中的后台 framebuffer
7. 程序等待合适的帧边界
8. 前后台 framebuffer 交换
9. RGB 外设通过 bounce buffer 和 DMA 持续读取像素
10. LCD 面板显示完整照片
```

这条链路中：

- JPEG 是 Flash 里的压缩文件；
- framebuffer 是 PSRAM 中已经展开的完整画面；
- ESP32-S3 负责解码、控制和页面逻辑；
- DMA 与 bounce buffer 负责稳定搬运像素；
- LCD 只负责把收到的像素显示出来。

最重要的五句话：

1. **ESP32-S3 负责执行和控制。**
2. **Flash 负责断电后仍然保存程序、设置和文件。**
3. **RAM / PSRAM 负责运行时的临时工作，断电后内容消失。**
4. **Framebuffer 是 RAM 中一张展开成像素的完整屏幕画面。**
5. **LCD 不理解页面，只会持续显示收到的像素。**

## 15. 为什么正式界面改用 LVGL

手写 `Paint_*` 页面虽然验证了双 framebuffer，但大面积逐像素绘制导致切页约 3–4 秒，期间主循环无法继续处理触摸。长期方案改为 LVGL 管理控件、排版和事件，底层继续使用已经验证的双 framebuffer、VSYNC、18MHz 像素时钟和 20 行 bounce buffer。

2026-11-11 完成第一阶段真机门禁：独立 LVGL 9.5 原型显示主页和大触摸按钮，按下反馈即时，无数秒阻塞、黑屏或残行。编译占 Flash 23%，内部动态内存 26%。这证明成熟 GUI 框架与当前显示驱动可以共同工作，后续功能应在该基线上扩展，不再美化旧手写页面。

## 16. 最小状态原型与深色画面抖动

第二阶段建立了三个可复用的 LVGL screen：

- `HOME`：主动查看的主页；
- `SETTINGS`：设置页，停留期间暂停自动待机；
- `AMBIENT / IDLE DISPLAY`：中文可称“待机展示”，主页 60 秒无触摸后自动进入，点击任意位置返回主页。

真机验证中，状态切换、触摸和返回逻辑全部正常。深色渐变版本与去掉渐变后的深色纯色版本都会明显抖动，而改为与主页相同的浅色背景后基本不可见。这次对照说明：

1. 抖动不是由 Wi-Fi 上传或 JPEG 解码引起，因为状态原型未启用这些功能；
2. 抖动不是渐变或透明效果单独造成，因为纯色深色页也会出现；
3. LVGL 状态机与页面切换不是直接原因，因为浅色页使用相同的 screen 和切换逻辑却稳定；
4. 更可能是 RGB LCD 持续扫屏时存在轻微波动，深色大色块和清晰边界使它更容易被人眼发现。

因此浅色界面只能用于定位问题，不能作为正式工程基线。用户上传的照片不可控，产品必须支持深色主题和全屏深色照片。第二阶段显示稳定性门禁保持未通过，先按单变量顺序测试 DMA burst、像素时钟、同步时序、bounce buffer 和 PSRAM 传输，再继续功能开发。
